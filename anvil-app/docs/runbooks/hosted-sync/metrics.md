# Hosted sync observability and alerts

The Worker emits application metrics as JSON strings through `console.log`.
Workers Observability stores the message; it does not automatically turn
these application-specific values into D1/R2 or billing alerts. This guide
sets up the views, native platform alerts, and the external alert route needed
for the thresholds below. Record the selected environment, Worker name,
notification policy IDs, destination, and responder in the launch record.

## Confirm collection

Use the target generated by the hosted deployment wrapper:

```sh
cd anvil-app
export HOSTED_ENV=staging # Set to production when checking production alerts.
TARGETS=cloud/backend/.wrangler/hosted-targets.json
export WORKER_NAME="$(jq -er --arg env "$HOSTED_ENV" '.environments[$env].workerName' "$TARGETS")"
export CONFIG="$PWD/cloud/backend/.wrangler/mesh/$WORKER_NAME/wrangler.jsonc"
export MESH_ORIGIN="$(jq -er --arg env "$HOSTED_ENV" '.environments[$env].baseUrl' "$TARGETS")"
pnpm --dir cloud/backend exec wrangler tail "$WORKER_NAME" --format json --config "$CONFIG" |
  jq -c '.logs[]?.message // empty' |
  jq -R 'fromjson? | select(.metric != null)'
```

Leave this running. In a second terminal, repeat the environment, target, and
`MESH_ORIGIN` assignments above, then send a harmless unsigned request to the
webhook endpoint:

```sh
export MESH_ORIGIN='<the selected target baseUrl>'
curl -sS -o /dev/null -w '%{http_code}\n' \
  -X POST "$MESH_ORIGIN/v1/hosted/stripe-webhook" -d '{}'
```

When Stripe secrets are installed, the request should return `401` and the
tail should show `webhook.rejected` with `reason: "signature"`. `404`
indicates that the hosted webhook binding or secret is absent; resolve that
configuration before counting the check as passed. Never paste the tail into
a ticket without checking for secrets or user data first.

For stored logs, open **Workers & Pages → <selected Worker> → Observability →
Logs** and search for message text such as `"metric":"webhook.rejected"`.
These JSON messages are strings, so filter the log message text; do not expect
`metric` to be a top-level structured field. Save queries for the
`webhook.event`, `webhook.backlog`, `webhook.failed`, `reconcile.run`,
`reconcile.failure`, `reconcile.freshness`, `config.issue`, and
`sweep.error` messages. The hourly sweep runs at minute 17; allow one full
hour after deployment to verify its signals.

If stored logs do not appear, open the generated Wrangler config and confirm
Workers observability is enabled. Workers Logs need the `observability`
setting; newly created Workers have it enabled by default, while older
Workers may not. Treat absence as a deployment/configuration gap, not as zero
errors. See [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
and the [Query Builder](https://developers.cloudflare.com/workers/observability/query-builder/).

## Configure notification routes

1. In **Cloudflare Dashboard → Notifications**, select a route that reaches
   the named operator. Email is available on all plans; PagerDuty and generic
   webhooks depend on account plan and notification-service setup. Test the
   route using the notification service's test action where available and
   record who received it.
2. Add a `Workers Observability Alert` notification for the selected account
   and configure it to notify the same route. This covers Worker observability
   alerts such as runtime errors; verify the policy is enabled and its policy
   ID is recorded. Cloudflare's alert does not replace a monitor for the
   public descriptor URL or custom billing metrics.
3. Add an external uptime check for
   `$MESH_ORIGIN/.well-known/anvil-backend`. Expect HTTP 200 and a parseable
   descriptor. The service runs on a `workers.dev` origin, so Cloudflare's
   zone-based HTTP traffic alerts are not the availability check for this
   Worker.
4. Forward Workers logs or JSON metric messages to the chosen alert-capable
   monitoring service using OpenTelemetry, Logpush, or a Tail Worker. Create
   threshold rules for the custom signals in the table below, send a test
   event through the route, and record the resulting notification. Workers
   Observability saved queries are for investigation and dashboards; a saved
   query alone is not an alert rule.
5. In Cloudflare account billing/usage, configure available D1 rows-read and
   rows-written notifications plus an account budget alert that covers D1,
   Workers, and R2 spend. These are account-level cost guardrails, not
   per-database query-error alerts. Add a responder who can inspect D1 query
   analytics and Worker invocation logs.

Do not mark alerting complete until the destination, recipient, test
notification, and named responder are recorded. Alert ownership is not
configured by this repository. If the account credentials, notification
destination, or on-call owner are unavailable, record this gate as **blocked**;
manual log inspection is useful during testing but is not alert coverage.

## Signals and starting thresholds

| Signal | Worker metric/log | Warn | Page / action |
| --- | --- | --- | --- |
| Oldest unprocessed webhook | `webhook.backlog.oldestUnprocessedAgeMs` | > 15 min | > 1 h; keep Stripe deliveries enabled, inspect D1 and Stripe, then use [webhook-failures.md](webhook-failures.md) |
| Failed webhook events | `webhook.failed.lastHour`, plus `webhook.event.outcome` | > 5/h | > 20/h or a sustained `failed-deterministic` cluster; inspect event types and sanitized `last_error` |
| Reconcile freshness | `reconcile.freshness.staleAccounts` | any subscribed account > 12 h | any subscribed account > 24 h; verify cron and Stripe, then reconcile affected accounts |
| Reconcile failures | `reconcile.run.failed`, `reconcile.failure`, `reconcile.error` | any repeated failure | repeated failures or provider/D1 outage; check Worker, D1 and Stripe status |
| Stale checkout sessions | `checkout.stale.count` | > 20 open sessions older than 24 h | Review weekly; inspect Stripe dashboard before clearing anything |
| Unknown/outage-grace entitlement | `entitlement.decision.state/source` | > 1% for 15 min | > 5%, or outage-grace continues past 20 h; follow [entitlement-incidents.md](entitlement-incidents.md) |
| Billing-unavailable denials | `enforcement.denial.reason` | sustained non-zero | > 10/min; check D1 health and recent deploys |
| D1 query failures | Worker exceptions/logs and D1 analytics | > 0.1% of queries | > 1% or a 5-minute sustained failure |
| Website-to-backend service-auth failures | `service_auth.failure` | > 10/h | > 100/h; verify selected key IDs in website and Worker settings, then consider probing |
| Production enforcement flag | deployed Worker variable | — | Anything other than literal `'true'`: immediate incident |
| Hosted Worker runtime failures | Workers invocation errors | investigate any spike | sustained 5xx, uncaught exceptions, or exceeded resources |
| D1/R2 spend and capacity | Cloudflare account usage | account-approved budget | page at account-approved ceiling; inspect rows, storage, and artifact bytes |

Thresholds are initial values for low traffic and should be tuned after
observing real usage. The hourly sweep emits aggregate D1 metrics; individual
`webhook.event` logs report outcomes at delivery time. Repeated deterministic
rejects get HTTP 200 so Stripe does not retry poison events; use
[webhook-failures.md](webhook-failures.md) for repair.

## Signal inventory

| Metric | Fields |
| --- | --- |
| `entitlement.decision` | `state`, `source`, `reason`, `cached`, optional `outageFallback` |
| `enforcement.denial` | `reason` |
| `webhook.event` | `type`, `outcome` (`processed`, `duplicate`, `failed-deterministic`, `failed-fault`) |
| `webhook.rejected` | `reason` |
| `service_auth.failure` | `path` |
| `hosted.route_error` | `path` |
| `config.issue` | `missing` |
| `reconcile.run` | `candidates`, `attempted`, `reconciled`, `failed` |
| `reconcile.failure` | no account identifiers |
| `reconcile.skipped` | `reason` |
| `reconcile.error` | `stage` |
| `webhook.backlog` | `oldestUnprocessedAgeMs` |
| `webhook.failed` | `total`, `lastHour` |
| `checkout.stale` | `count` |
| `reconcile.freshness` | `staleAccounts` |
| `sweep.error` | `signal` |

The hourly cron reconciles at most 10 Stripe accounts per run and examines at
most 50 candidates. Per-account reconcile markers become due after 12 hours;
the freshness alert threshold is 24 hours.

## Log hygiene

Never log service or Stripe secrets, signature values, enrollment/link codes,
raw synced content, card/payment details, email addresses, WorkOS identities,
or per-user billing data. `webhook_events.last_error` and
`billing_audit.detail` are intentionally sanitized. Keep that boundary when
adding fields or forwarding logs to a third party.
